# スコアランク（成绩评价）算分公式与门槛

`/rtlink improve`、`/rtlink score` 和管理端输出的「评价」都指街机版的 **スコアランク**。
本文记录该体系的算分公式、8 档门槛、数据来源，以及本插件是如何验证它的。

---

## 1. 结论

### 1.1 算分公式（AC16 ニジイロ～）

```
スコア = 良 × 基本点 + 可 × ⌊基本点 / 2⌋ + 黄色連打打数 × 100
```

| 量 | 含义 | 取值 |
| --- | --- | --- |
| 基本点 | 单个音符的满分 | 每谱固定常数，**10 的整数倍** |
| 天井スコア | 全良时的分数上限 | `总音符数 × 基本点`，约 100 万（实测 98.4 万 ~ 100.5 万） |
| 極スコア | 最高档「极」之上的门槛 | `天井スコア + 必要連打打数 × 100` |
| 黄色連打 | 每打固定分 | **100 分/打**，不计入总音符数、不影响 combo 与魂槽 |
| 可 | 良的一半，个位截断 | 良 330 → 可 160 |

要点：

- **ニジイロ 取消了ゴーゴータイム加分与初項/公差（连击加分）**，分数只取决于判定构成与连打打数。
- 「总音符数」**不含黄色連打 / 风船 / くすだま**，因此 `谱面 totalNotes == 良 + 可 + 不可` 恒成立。
- 基本点由谱面设计者按「天井スコア接近 100 万」来定，因此**不能**简单地写成 `1,000,000 ÷ 总音符数`；
  本插件优先使用 wiki 实测的每曲天井スコア，缺失时才退回该式估算。

### 1.2 8 档门槛

除最高档外，门槛是**固定分数**，与该谱的天井スコア无关：

| rank | 名称 | 门槛 |
| --- | --- | --- |
| 1 | 无 | < 500,000 |
| 2 | 白粹 | ≥ 500,000 |
| 3 | 银粹 | ≥ 600,000 |
| 4 | 金雅 | ≥ 700,000 |
| 5 | 粉雅 | ≥ 800,000 |
| 6 | 紫雅 | ≥ 900,000 |
| 7 | 极 | ≥ 950,000 |
| 8 | 极+连打满 | ≥ 该谱 **極スコア**（要求全良 + 规定连打打数） |

门槛定义在 `score_rank.py` 的 `SCORE_RANK_BORDERS`；如需修正，改这一处即可。

> **为什么不是天井的百分比？** 早期版本曾按「天井スコア × 50/60/70/80/90/95%」实现，这是错的。
> 反证：实测数据中 2 档的最低分是 **512,890**。若门槛是「天井 × 50%」，该谱天井需要 ≥ 1,025,780，
> 而 wiki 的配点设计是让各曲天井**接近 100 万**，全库最高约 100.8 万（見 `極スコア表`），
> 根本达不到这个量级；3 档同理（608,680 ÷ 60% = 1,014,467，同样越界）。
> 反过来，固定门槛完全吻合实测：各档之间的分数空隙精确跨过 50/60/70/80/90/95 万
> （1→2：472,900 → 512,890；2→3：584,820 → 608,680；3→4：699,230 → 703,600；
> 4→5：798,830 → 802,020，四条边界无一例外）。
> 该反证已固化为测试 `test_bundled_ceilings_rule_out_a_ratio_model`。

## 3. 验证过程与证据

用插件 `cache/scores_hiroba.json` 中一份真实的 1660 条成绩快照（1390 条能与谱面库匹配）做反向验证。

### 3.1 算分公式

- `良 + 可 + 不可 == 谱面 totalNotes`：**1389 / 1390 条精确成立**，确认总音符数不含连打。
- 取 14 条「全良」（可 = 不可 = 0）记录反推基本点 `(分数 − 连打×100) ÷ 良`：
  得到 2490 / 4430 / 6790 / 1980 / 3630 …，**全部落在 10 的整数倍上**（巧合概率为零），
  且与 `1,000,000 ÷ 总音符数` 高度吻合（如 1980 vs 1980.2、4810 vs 4807.7）。
- 全库反推中 **60.9% 的谱面精确落在 10 的整数倍**，另有 0.7% 为整数但非 10 的倍数——
  剩余偏差来自「可」的个位截断与成绩字段可能取自不同次演奏。

### 3.2 门槛分档

用每曲 wiki 天井スコア计算 `分数 ÷ 天井スコア`，与 API 返回的 `best_score_rank` 对照：

| rank | 样本 | 比例下界 | 比例上界 | 分数下界 | 分数上界 |
| --- | --- | --- | --- | --- | --- |
| 3 | 6 | 60.89% | 68.91% | 608,680 | 699,230 |
| 4 | 38 | 72.44% | 80.03% | 703,600 | 798,830 |
| 5 | 131 | 80.19% | 90.40% | 802,020 | 904,140 |
| 6 | 187 | 90.02% | 95.75% | 900,800 | 956,670 |
| 7 | 782 | 95.01% | 102.01% | 950,650 | 1,005,670 |
| 8 | 197 | 100.00% | 111.17% | 1,000,080 | 1,112,070 |

（另有无档 1 的 1 条、白粹 2 档的 8 条：472,900 以下，以及 512,890 ~ 584,820。）

- **判据在「分数」列，不在「比例」列。** 分数列的相邻空隙全部精确跨过整十万：
  472,900 → 512,890（跨 50 万）、584,820 → 608,680（跨 60 万）、
  699,230 → 703,600（跨 70 万）、798,830 → 802,020（跨 80 万）。
  比例列则会随各曲天井在 98.4 万 ~ 100.5 万之间浮动，无法给出这种整齐的分界。
- **rank 8 ⟺ 分数 ≥ 極スコア：979 / 979 完全吻合（100%）**，无一例外。
- 按本文门槛表反推评价，与 API 的 `best_score_rank` **一致率约 98.3%（1366 / 1390）**。

## 4. 已知偏差

1. **约 24 条 / 1.7% 的残余不一致**（例如分数已 ≥ 950,000 但 API 仍给 6 档）。
   这些不一致只朝一个方向：分数暗示的评价**高于** API 给的值。
   最可能的原因是 `best_score_rank` 与 `high_score` 来自不同批次的数据刷新
   （分数先更新、评价等级后更新），属于接口侧的数据时序问题，而非门槛本身。
   实际影响：极少数歌可能晚一档被判定为「已达目标」。
2. **`pound_cnt` 等判定字段可能来自与 `high_score` 不同的一次演奏**：
   同一时间戳下 `分数 − 基本分` 也不总等于 `连打 × 100`。因此 `/rtlink improve` 的
   「所需良数」是由**分数缺口 ÷ 基本点**推出的等效值（稳健），而不是直接对当前良/可计数做差；
   「当前还有几个可」只作为可行性参考。
3. **最高档（rank 8）不可用「转几个可」描述**：它要求全良 **且** 补足该谱规定连打打数，两者是「且」关系。
   代码中由 `pathRequiresAllGood` 标记，输出会明确写成「需全良 + N 打连打」。
4. **游戏给的评价优先于本地门槛**：判断「是否已达某评价」时以 API 的 `best_score_rank` 为准
   （`analyze_rank_improvements` 与 `annotate_target`），本地门槛只用来推算「还需要多少分」。
   这样即使门槛仍有偏差，也不会把游戏里已经升档的歌列进「待提升」。

## 5. 如何修正或更新

1. 只改门槛：编辑 `score_rank.py` 的 `SCORE_RANK_BORDERS` / `SCORE_RANK_NAMES`。
2. 更新每曲数据：重跑 `python scripts/build_score_rank.py`，会刷新
   `resource/score_rank.v1.json.gz` 与 manifest 中的覆盖率统计。
3. 谱面库换代后：先按 README「重新构建谱面数据」更新 `charts.v1.json.gz`，再重跑上面的脚本，
   匹配率会随之提高。
4. 回归验证：`python -m pytest test/test_score_rank.py -q`。
